# Contact creation: small introduction, rich memory

## Design intent

A contact is a person worth remembering, not a completed database record. The first screen should let someone finish in seconds, without knowing what a country override, preferred channel, or phonetic name is.

Use the existing Kin Material 3 system: Bricolage display headlines, Figtree interface text, botanical primary, quiet tonal surfaces, generous touch targets, and rounded grouped fields. One clear filled action stays available above the keyboard. Manual creation needs neither a network nor AI. Optional description extraction uses Android’s installed model through its normal AICore binding permission, without a new runtime permission or internet access. Avoid a mandatory mode chooser or multi-step wizard.

## Describe → review → save (on-device)

When an already-installed model is ready, a new empty contact offers **Contact description**, **Create draft**, and **Add manually**. Otherwise it opens the manual form directly: no AI warning, setup screen, retry action, or extra tap. The manual form is usable while availability is checked; focusing/typing in it or opening an optional field keeps it manual even if the model becomes ready later. For example: “John Doe from SoAndSo Startup +11234567890. Met at Climate Week.” A successful extraction opens the compact editable form, headed **Review contact**. It does not save anything. The original description remains available for comparison; only the reviewed card fields are saved. Prefilled intents and existing-contact edits use forms directly. The same form is used regardless of who is holding the phone.

`NanoContactDescription` uses ML Kit’s `genai-prompt:1.0.0-beta4` to access Gemini Nano via AICore. It checks for the installed/enabled `com.google.android.aicore` package, then checks feature status on opening and again before inference. Missing/disabled AICore, a missing model, feature unavailability, a failed service check and a timed-out check are classified internally but all silently use the manual form. Availability is checked again when opening a fresh contact. Only `FeatureStatus.AVAILABLE` permits inference. `DOWNLOADABLE`, `DOWNLOADING`, unavailable hardware, setup errors, and check timeouts offer manual entry instead. The app never calls `download()` or `warmup()`, bundles no model, adds no API key/cloud client, and retains the manifest’s removal of `INTERNET` and upload telemetry. Android can independently manage its own AICore updates; MyPeople does not control or initiate those.

Only the explicitly entered description is passed to the model—not contacts, relationship history, notes from existing people, or credentials. The prompt asks for allowlisted JSON fields, with every value quoted directly from the source. A strict local parser rejects ungrounded strings, malformed/truncated JSON, unexpected properties, multiple-person output, missing names, and oversized output. Phone text and the chosen local-number region are not rewritten. This is prompt-based JSON extraction, not a guarantee of semantic correctness: a name mentioned as a referral could still be attributed incorrectly, so review is mandatory. No generated actions, tool calls, merges, store writes, or enrichment run during extraction.

Entry is limited to 2,000 characters and inference to 30 seconds. Errors retain the source; Add manually cancels in-flight extraction and cannot be overwritten by a late result. Back/Cancel also protects an unsaved description. The source and draft survive configuration changes but are not a durable draft inbox. Extracted meeting context becomes visible, editable contact notes; manually editing those notes does not trigger further AI processing. Newly added profile links retain the existing explicit-save confirmation policy.

Platform documentation: [Prompt API setup and availability](https://developers.google.com/ml-kit/genai/prompt/android/get-started), [device support](https://developers.google.com/ml-kit/genai/#device-support). A compatible phone with an already-installed AICore model is required; this is not universal Android functionality.

## Storyboards

Manual-entry rows start after **Add manually** on AI-ready devices; otherwise the form opens directly. There is no separate self-entry or phone-handoff mode.

| Moment / motivation | Before → action → result | Design response |
| --- | --- | --- |
| Capture a whole introduction in one thought | Type/paste the description → Create draft → review/correct extracted fields → Save | Already-installed on-device model only; original input available for comparison, no automatic save, manual fallback for unsupported devices or extraction failures. |
| An introduction in a noisy conference hallway | Meet → tap New contact → enter name and number → save before the conversation moves on | Name first, phone/email already available, appropriate keyboards, no mandatory photo or contact method. |
| Hand my phone to someone | Open New contact → hand over → they enter their details in the same form → review together → Save contact | The same labels, optional fields and Save action as entering someone’s details myself. No mode chooser, guest form, thank-you screen or hand-back step. |
| Someone prefers LinkedIn/a website to sharing their number | Add a profile or website link → paste it → save | A link is optional; neither a phone number nor an email is required. Explain profile-discovery/photo-lookup use. |
| Remember a person without asking for contact details | Enter a first name or useful remembered name → optionally note where we met → save | Name-only contacts are valid. Context is optional, not a required phone/email validation error. |
| Capture a professional introduction | Enter name/email → Work / Note chips → company, role, where we met → save | Work and memory sit together, without confronting everyone with job fields. |
| A friend recommends a plumber, doctor, babysitter, etc. | Enter the name I will recognize → number → context such as “recommended by Jo” | Free-form name supports people and useful business names; contact notes preserve the referral without AI processing. |
| Copy details from a message or email | Paste name and contact point → optionally add a link → save | Standard Android paste/autofill behavior, explicit field labels, email/phone/URL keyboards; no speculative parsing that could silently misclassify pasted text. |
| Android sends a prefilled create/edit-contact intent | Open populated form → inspect essentials → review additional details → save | The compact form preserves every prefilled field and warns when additional details exist; More details exposes the full editor. Editing an existing contact still starts in the complete editor. |
| Meet someone from another country | Enter +country number, or choose the country by searchable name → save | New manual cards default to a supported device-locale country (US fallback). Imported card regions are preserved. Full international numbers work regardless of the local-number default. Invalid-looking numbers get a non-blocking warning; entered text is retained. |
| Add a birthday, postal address, multiple numbers, photo, or name pronunciation | More details → fill only what matters → Save | Progressive disclosure retains the existing complete editor and per-number labels/country overrides. Back to essentials does not discard hidden values. Photo selection no longer requires entering a name first. |
| Interrupted by a call, rotation, keyboard, or accidental Back | Draft stays during the editor lifetime/configuration change → return and continue; cancellation with edits asks before discarding | ViewModel draft, saveable disclosure state, discard confirmation, IME-aware sticky action. This is not a durable draft inbox: process death is not guaranteed to restore an unsaved draft. |
| I already know this person / accidentally create them twice | Save locally → existing duplicate detection surfaces candidates in Review → explicitly decide whether to merge | Preserve the existing review/merge safety path. No automatic merge or automatic prefill from another person’s record. Pre-save duplicate suggestions are not implemented by this change. |
| Several introductions at the same event | Save → return to People → New contact → repeat | Capture remains short. A dedicated Save-and-next/event batch flow is a follow-up, not a claim of this implementation. |
| No signal / save fails | Save locally → success; on error remain in editor with details intact → fix/retry | Existing offline transaction path, trimmed required name, no empty placeholder contact points, visible announced error, duplicate-submit guard. |

## Manual/review form hierarchy

1. Quiet centered **New contact** chrome, with a close icon labelled Cancel (or **Review contact** after description extraction). Edge-to-edge system bars follow the light/dark surface.
2. A compact botanical identity panel: the editable name fills the available height without a slogan. A cookie-shaped portrait shows live initials or the selected photo; tapping its edit badge offers Take photo or Choose photo without visiting the complete editor. The full editor and saved-contact photo chooser offer the same source choices. No oversized introductory headline or handoff action.
3. **Stay in touch** groups optional phone and email into quiet rounded tonal rows, with icons and separators instead of a stack of outlined boxes. The country selector stays inline unless large text or a narrow screen needs a separate row. Existing per-phone overrides are displayed and edited correctly without changing hidden numbers.
4. **Make it personal** offers Link, Work and Note chips. Each reveals only its own fields, with restrained spring expansion and fade. Closing a chip never deletes data. There is no all-at-once context questionnaire.
5. More details opens the complete editor; hidden values are preserved. The compact form uses 16 dp outer padding, 28 dp group corners and 8/12 dp internal rhythm, without shrinking Material touch targets. Decorative initials are omitted at large font scales to prioritize the editable name.
6. One persistent 56 dp **Save contact** action with a check mark, or an inline progress indicator during saving/extraction. It stays above the keyboard. No guest-specific completion or host-review gate.

Notes are not processed by background AI, but are **not secret from exports/sync**. Optional description extraction processes only the text explicitly submitted on-device and can propose a quoted context note. The UI says so rather than describing them as private. User-added profile links retain the existing manual website confirmation policy.

## One shared experience

Handing the phone to someone does not change the app’s behavior. The form does not hide notes, restrict optional fields, or gate saving based on who is using it. Save follows the normal navigation into the saved person. This is not a lock or privacy boundary; use Android’s device-level safeguards if needed.

## Camera photos

Take photo requests the existing Camera permission only on that explicit action and launches Android’s camera with `TakePicture` and a scoped FileProvider URI. Choose photo keeps the existing library/document picker; declining permission or cancelling capture never replaces a photo. No storage/gallery permission is added.

New captures are temporarily stored in app-private `cache/contact-camera/`, sampled and resized to a maximum 1280 px edge, corrected for all eight EXIF orientations, and re-encoded as JPEG below the contact’s 2 MiB limit. GPS and other EXIF metadata are not copied into the contact. Camera files are deleted after success/cancellation/failure; abandoned captures are cleaned after a day when taking another photo. MyPeople does not publish the temporary original to the gallery. Permission denial, capture/confirmation, portrait preview before entering a name, and deletion of the capture file were exercised with an emulator’s synthetic camera; no physical-device camera was opened during development. Existing imported originals are untouched. In the editor, capturing only changes the draft; Save contact remains explicit. The existing saved-contact photo chooser retains its normal save behavior.

## Verification

- Render-only Compose tests exercise essential-field editing without losing secondary fields, shared context/details access, name-only/no-placeholder behavior, independent Work/Note disclosure without data loss, inline photo action/disabled states, camera-versus-library source selection and cancellation, synthetic EXIF orientation/GPS stripping, resize limits, and scoped camera URI sharing, 200% text with accessible country selection, and country/override selection without rewriting numbers or hidden fields.
- JVM extraction tests cover quoted Unicode fields, exact phone/extension preservation, unsupported/ungrounded values, multiple-person output, malformed JSON, size limits and untrusted input quoting.
- A fresh, opted-in disposable-emulator editor test uses a fake model to exercise shared-form manual creation, absence of handoff modes, description → editable review → explicit save, automatic manual entry for every non-ready AI status, extraction failure, cancellation without late draft overwrite, and preserving a manual entry when a delayed availability check succeeds. Synthetic graph commits remain until the disposable installation is uninstalled; the test does not bypass durable-history restore safeguards.
- Read-only checks on a Pixel 10 confirmed that supported hardware alone is not sufficient: AICore was absent in that phone profile. No AICore reset, model download, or personal-store test was performed.
- Visual inspection on a fresh API 37 emulator checked the expressive form in light and dark, live initials, keyboard-visible sticky Save, and 160% text layout. The real AICore availability check was also exercised on the emulator and correctly offered manual entry. Actual Gemini Nano inference quality and latency still require testing on a supported physical phone with the model already installed; fake-model/emulator tests do not verify inference quality.
- Check small screens, keyboard-visible entry, large text, light/dark, TalkBack labels, country changes, full-detail round trips, and failed-save retry when changing this flow.
